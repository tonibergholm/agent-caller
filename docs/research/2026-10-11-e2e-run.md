## Isolation, and two leaks

Scratch environment under `/tmp/ace2e` (acd hook port 52955, client port 52956, T3 52957, herdr session `ace2e`
in its own tmux server). The desktop T3 and the default herdr session were not touched.

**Leak 1: the scratch herdr socket was visible to the user's acd.** The user's acd scans
`~/.config/herdr/sessions/*/herdr.sock`. The first two bring-ups put `ace2e` there; the user's acd logged
`herdr socket found` at 09:43:17Z and `socket gone` at 09:46:17Z. No agent ran in that session. After that herdr
ran with `HOME=/tmp/ace2e/home`, so its socket is outside the scanned directory.

**Leak 2 (traffic to the user's acd): the recommended Claude isolation does not work.** Two Claude sessions were
started before this was understood.

- `claude --setting-sources project,local --settings <scratch>`: `/hooks` in that session listed `[User]` http hooks
  to `http://127.0.0.1:47801/hook/claude/...` (the user's acd) next to the scratch ones on 52955. The user settings
  are loaded despite `--setting-sources`.
- Adding `allowedHttpHookUrls: ["http://127.0.0.1:52955/*"]` to the `--settings` file did not stop them either.
- Result: two stale agents appeared in the user's acd for cwd `/private/tmp/ace2e/proj` (`proj-2e` Idle,
  `proj-77` NeedsYou), created by the `SessionEnd` hooks. acd keeps a session for `end_grace` (10 min) after
  `SessionEnd`. They were gone from `acd status` between 13:05 and 13:08. The user's acd was only read with `acd status`
  (`env -u ACD_CONFIG_DIR`); it was never signalled or reconfigured.
- Fix used for all later Claude runs: `sandbox-exec` with `(deny network-outbound (remote tcp "*:47801"))`
  (profile semantics checked first against a canary listener on a scratch port). On screen:
  `UserPromptSubmit hook error  connect ECONNREFUSED 127.0.0.1:47801` and
  `Stop hook error: connect ECONNREFUSED 127.0.0.1:47801`, while the scratch URL on 52955 delivered
  `UserPromptSubmit` and `Stop` to the scratch acd. After the run `acd status` of the user's acd showed
  `agents: 0`, the same as the baseline before the sandboxed sessions.
- T3: `t3 serve` cannot run under `sandbox-exec` (`spawn EPERM` in its OpenCodeServerLedger), so the server runs
  normally and its Claude provider is pointed (`providerInstances.claudeAgent.binaryPath`) at a wrapper that runs
  claude under the same profile. User's acd: still 0 agents afterwards.

**Codex isolation (no leak).** `codex app-server` `hooks/list` (read-only, runs no hook) shows the user's
`~/.codex/hooks.json` acd entries as `untrusted` (only the herdr `SessionStart` entry is `trusted`), so Codex does
not run them. `-c` cannot grant project trust or hook trust (tried `projects."...".trust_level` and
`hooks.state` through `-c`: not applied; session-flag hooks stay `untrusted`). So `codex-trust.sh add` appended
project-trust and hook-trust entries for `/private/tmp/ace2e/proj` to `~/.codex/config.toml` after a backup, and
`down.sh` restored the file (sha256 `946dd1a13f3c379a...` before and after). The `/hooks` screen of the test
session showed `PermissionRequest: Installed 3, Active 2, Review 1` (warp plugin + scratch project active, the
user's acd entry waiting for review). I chose "Continue without trusting" at the review prompt and never "trust all".
The user's acd showed no Codex agent during or after the runs. One earlier Codex start (before the trust entries
matched the `/private/tmp` path) only reached the review screen and exited.

Other residue outside `/tmp/ace2e`: `~/.claude.json` has a trust entry for `/private/tmp/ace2e/proj` (written by
Claude on the trust dialog), transcripts under `~/.claude/projects/-private-tmp-ace2e-proj*`, Codex rollouts under
`~/.codex/sessions/2026/10/11/`, and a scratch OpenCode/pi start in the scratch cwd. `~/.claude/settings.json`
and `~/.codex/hooks.json` kept their 12:35 mtimes (before this run started); `~/.codex/config.toml` was restored.

## Method

- Panes were driven with `herdr pane run/send-text/send-keys/read`; Claude and Codex were launched with the real
  `HOME` (login) in a clean environment (the herdr server starts from `env -i`, so no `CLAUDE_*` is inherited).
- `inbox.py` speaks acd/1 over `acd.sock`; one logger connection records every server message to `inbox.jsonl`
  (other invocations write there too, filtered by `who`).
- Only `touch /tmp/ace2e/x-*.txt` was approved.
- The user's acd was read only through `acd status` (before: 0 agents; after the sandboxed runs: 0 agents).

## Bugs and findings

1. **A Claude `Esc` on a held permission dialog resolves `uncertain` after about 30 s** (three of three runs in a
   row; P3 check 3 measured 1.7 s, and two earlier runs today ended `terminal` after about 2 s and about 20 s).
   The card should switch to `terminal` within 2 s (14.4). While it stays open, the agent card is stuck on a
   request that no longer exists. Evidence: `inbox.jsonl`, 13:12 to 13:14, `request.resolved {by: "uncertain"}`
   at +33 s, +33 s, +33 s after the keys. Not isolated further (the run had a foreign `PermissionRequest` hook and the
   user's hooks in the session; P3 had neither).
2. **Codex: a delivered No leaves the request `answering` for about 33 s, then `uncertain`.** Denying a keys request
   makes Codex show `You canceled the request ... Conversation interrupted` and fire no `PostToolUse` or `Stop`
   hook, so there is no evidence. Meanwhile `agent.send` returns `agent_busy` and the agent shows a pending card.
   Evidence: `r5`: keys sent 10:04:04.45Z, `agent.updated` `pending answering` with state `idle` from 10:04:04.65Z,
   `request.resolved by uncertain` at 10:04:42.31Z (38 s). The same happened in the later run (32.8 s and 33.4 s).
   The screen already shows the dialog gone; the screen read could be the evidence.
3. **Codex lifecycle hooks may add 1.5 s when acd is stalled, above the 1 s of §14.6.** The shim budget is 800 ms for
   `PermissionRequest` and 1500 ms for the others (`hook_shim.rs`, matching §6.3's 2 s Codex timeout); measured
   1534 to 1553 ms. Live, a stalled acd made a Codex approval dialog appear after 6.7 s against about 3 s. Claude's
   installed timeouts are 1 s, so Claude meets 14.6. Either lower the shim budget to 1 s for lifecycle events or
   change 14.6 for Codex.
4. **Claude isolation recipes in the task do not work** (`--setting-sources project,local`, `allowedHttpHookUrls`):
   user-level http hooks still load and reach the user's acd. This is a harness finding, but also a user-facing one:
   a Claude session started with a second `--settings` still sends the user's configured hooks. Related: acd keeps a
   ghost agent for 10 min after a `SessionEnd` from a session it had never seen.
5. **Restart behavior.** Requests on screen reappear only as `blocked_unparsed`, read-only, after a restart (the hook
   context is lost); the spec says "requests still on screen reappear", which holds, but they are not answerable
   from the inbox. A hold expiry on the other hand converts a held `hook` request into an answerable `keys` request.
6. **`request_not_ready` right after `request.opened` for a question** (keys path): the first answer got
   `request_not_ready`; it was accepted 523 to 657 ms later. Expected by §6.2 but a client must retry.
7. **Request ids restart at `r1` per epoch** and repeat across restarts; a log reader must key on `(epoch, id)`.
