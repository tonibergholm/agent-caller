## Bugs and findings

1. **A Claude `Esc` on a held permission dialog resolves `uncertain` after about 30 s** (three of three runs in a
   row; P3 check 3 measured 1.7 s, and two earlier runs today ended `terminal` after about 2 s and about 20 s).
   The card should switch to `terminal` within 2 s (14.4). While it stays open, the agent card is stuck on a
   request that no longer exists. Evidence: `inbox.jsonl`, 13:12 to 13:14, `request.resolved {by: "uncertain"}`
   at +33 s, +33 s, +33 s after the keys. Not isolated further (the run had a foreign `PermissionRequest` hook and the
   user's hooks in the session; P3 had neither).
2. **Codex: a delivered No leaves the request `answering` for about 33 s, then `uncertain`.** Denying a keys request
   makes Codex show `You canceled the request ... Conversation interrupted` and fire no `PostToolUse` or `Stop`
   hook, so there is no evidence. Meanwhile `agent.send` returns `agent_busy` and the agent shows a pending card.
   Evidence: `r5`: keys sent 10:04:04.45Z, `agent.updated` `pending answering` with state `idle` from 10:04:04.65Z,
   `request.resolved by uncertain` at 10:04:42.31Z (38 s). The same happened in the later run (32.8 s and 33.4 s).
   The screen already shows the dialog gone; the screen read could be the evidence.
3. **Codex lifecycle hooks may add 1.5 s when acd is stalled, above the 1 s of §14.6.** The shim budget is 800 ms for
   `PermissionRequest` and 1500 ms for the others (`hook_shim.rs`, matching §6.3's 2 s Codex timeout); measured
   1534 to 1553 ms. Live, a stalled acd made a Codex approval dialog appear after 6.7 s against about 3 s. Claude's
   installed timeouts are 1 s, so Claude meets 14.6. Either lower the shim budget to 1 s for lifecycle events or
   change 14.6 for Codex.
4. **Claude isolation recipes in the task do not work** (`--setting-sources project,local`, `allowedHttpHookUrls`):
   user-level http hooks still load and reach the user's acd. This is a harness finding, but also a user-facing one:
   a Claude session started with a second `--settings` still sends the user's configured hooks. Related: acd keeps a
   ghost agent for 10 min after a `SessionEnd` from a session it had never seen.
5. **Restart behavior.** Requests on screen reappear only as `blocked_unparsed`, read-only, after a restart (the hook
   context is lost); the spec says "requests still on screen reappear", which holds, but they are not answerable
   from the inbox. A hold expiry on the other hand converts a held `hook` request into an answerable `keys` request.
6. **`request_not_ready` right after `request.opened` for a question** (keys path): the first answer got
   `request_not_ready`; it was accepted 523 to 657 ms later. Expected by §6.2 but a client must retry.
7. **Request ids restart at `r1` per epoch** and repeat across restarts; a log reader must key on `(epoch, id)`.

## Diagnosis (stage A2, 2026-10-11 12:49 to 13:15)

Temporary `tracing::debug!` lines (target `e2ediag`) in `crates/acd-adapters/src/hooks/state.rs` were used and then
reverted; `git diff -- crates app` is empty. Same isolation as before (sandbox-exec deny for 47800/47801, herdr with

Scenario: `tests/e2e/scenarios/60-esc-diag.sh`.

### Bug 1: Esc on a held Claude dialog resolves `uncertain`

**Root cause: the Esc arrived before acd had matched the dialog on screen, so there was no capture and no
presence checking.** In all six runs the hold ended 62 to 75 ms after the `PermissionRequest` hook arrived, while the
only capture read so far had run at +1 ms, before the dialog was drawn, and the next read was scheduled 200 ms later.
`on_hold_ended` takes its "no capture" branch (`captured = track.pane.is_some() && track.capture.is_some()`), which only
keeps the occurrence open ("the hook stream owns attribution"). Claude fires no hook after an Esc, so the window
retires it `uncertain` at about 30 s (`Phase::HoldEnded { since }` with no evidence).

My stage A harness sent Esc as soon as the pane showed the dialog (`dlg` then `esc`, 62 ms after the hook), a
speed no person reaches but a fast `Esc` can reach. P3 check 3 pressed it by hand after more than a second.

Log excerpt, variant (b) run 1 (`r4`), real times:

```
10:54:26.488053Z  hook payload agent=Claude name=PermissionRequest ...
10:54:26.488203Z  spawn_read rid="r4" purpose=Capture pane=w2:p1
(+1 ms)           read NoMatch purpose=Capture  (screen tail: "manual mode on · esc to interrupt", no dialog yet)
10:54:26.562415Z  on_hold_ended rid=r4 expired=false captured=false pane=true capture=false     <- Esc, +74 ms
10:54:28.530696Z  on_screen rid=r4 purpose=Capture result="NoMatch" pane=true capture=false phase=HoldEnded
...                (capture reads keep returning NoMatch: the dialog is gone; no Presence read is ever spawned)
request.resolved by=uncertain, 30.2 s after the key
```

The same sequence holds for all six runs (hook to hold end: 72, 67, 71, 74, 67, 70 ms; resolved `uncertain` 30102 to
30253 ms after the key). `spawn_read` was never skipped (pane bound, permit and ticket available), and the matcher
returns `Matched` once the dialog is drawn: the first matching read comes about 205 ms after the hook.

Control: with Esc 1.5 s after the dialog is seen (`ESC_DELAY=1.5`), six of six runs resolved `terminal` in 1073 to
1845 ms. Branch taken: capture `Matched` at +205 ms (`capture` set), `Presence` reads while `Held`, `on_hold_ended
captured=true`, then `HoldEnded` read, then terminal resolution. Excerpt (`r7`):

```
10:57:03.170267Z  hook payload ... PermissionRequest
10:57:03.171170Z  read NoMatch (first capture read, dialog not drawn yet)
10:57:03.375597Z  on_screen rid=r7 purpose=Capture result="Matched" ... phase=Held
10:57:04.309216Z  spawn_read rid="r7" purpose=Presence
10:57:04.773264Z  on_hold_ended rid=r7 expired=false captured=true
10:57:04.773793Z  on_screen rid=r7 purpose=HoldEnded result="Matched"   ... resolved terminal ~1.07 s after the key
```

Both variants behave the same: with or without the foreign `PermissionRequest` command hook, fast Esc gives
`uncertain` (3 of 3 each) and delayed Esc gives `terminal` (3 of 3 each). The foreign hook is not a factor.

**Socket check.** acd's discovered socket is `/private/tmp/ace2e/home/.config/herdr/sessions/ace2e/herdr.sock`
(canonicalized). The hook's `X-Herdr-Socket` is the pane's `HERDR_SOCKET_PATH`; `owner.rs` canonicalizes it
before comparing, and every run bound the pane (`pane=true`). So there is no `/tmp` versus `/private/tmp`
mismatch and the herdr `HOME` change did not matter: every Claude run in stage A, including the ones that ended
`terminal`, came after that change (herdr moved to its own `HOME` at 12:48; the first Claude run was later). The
differing earlier results (`terminal` in about 2 s once, in about 20 s once, `uncertain` at about 30 s three times)
fit the same race (how soon after the dialog was drawn Esc arrived); this was not measured for those runs.

**Suggested fix directions (not applied).** If a hold ends with no capture yet, keep the capture read going (it
already polls for 2 s) and treat "Esc seen, then the dialog never matched and the screen shows an idle prompt" as
absence evidence; or run a presence-style read at hold end that resolves `terminal` when no dialog and no pending
tool are on screen. Alternatively retire `uncertain` sooner when a screen read shows the agent idle.

### Bug 2: Codex No leaves the request `answering`

Scenario: `tests/e2e/scenarios/61-codex-deny-capture.sh`. Fixture candidates under `tests/fixtures/herdr/`, each in a
`-visible.txt` (herdr `--source visible`) and `-detection.txt` (the source acd reads) pair:

- `codex-dialog-run{1,2,3}-*.txt`: the approval dialog before the answer;
- `codex-after-inbox-run{1,2,3}-{0.5s,1s,2s}-*.txt`: after `request.answer deny` from the inbox;
- `codex-after-esc-run1-{0.5s,1s,2s}-*.txt`: after Esc typed in the terminal;
- `codex-after-n-run1-{0.5s,1s,2s}-*.txt`: after `n` typed in the terminal.

What they show (identical in all variants and times, so the dialog is already gone at 0.5 s): the screen ends with

```
• I'll run exactly the command you specified and request elevated approval.
✗ You canceled the request to run touch /tmp/ace2e/x-fx-run1.txt
• Failed (exit 1) touch /tmp/ace2e/x-fx-run1.txt
  └ (no output)
■ Conversation interrupted - use /feedback if something went wrong

› Ask Codex to do anything
  GPT-5.6-Terra low · /private/tmp/ace2e/proj · Run touch command
  ? for shortcuts
```

so a cancellation signature is the pair `✗ You canceled the request to run <command>` followed by
`■ Conversation interrupted`, with the dialog text (`Would you like to run the following command?`) absent and the
idle composer back. The inbox No, a terminal Esc and a terminal `n` are indistinguishable on screen. Because the
fixtures carry scrollback of earlier cycles in the same session, a matcher must key on the last occurrence and
the command text of the request being tracked. Note that Codex hooks fire nothing after a cancel, so this screen
is the only evidence.
