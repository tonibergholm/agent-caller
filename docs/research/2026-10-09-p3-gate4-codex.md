# P3 gate 4: Codex hook to pane binding (live checks)

Date: 2026-10-09
Spec: `docs/superpowers/specs/2026-10-07-agent-inbox-design.md` §6.1 to §6.4, §11 gate 4
Versions: Codex CLI 0.162.0, herdr 0.9.3. Model `gpt-5.6-terra` (reasoning low; picked from `models_cache.json`
as the smallest listed). Every turn was "Reply with just the word X" (6 turns, no tool use, no approvals).

Method (P0 precedent): isolated herdr session `p3x` in detached tmux, project-local
`.codex/hooks.json` in `/tmp/acp3/codex/d1` (SessionStart, UserPromptSubmit, PermissionRequest, PostToolUse, Stop),
a hook shim that adds `_env` (the `HERDR_*` variables and `CODEX_THREAD_ID`) and POSTs to a throwaway listener on
127.0.0.1:47961 (`python3 -I`, empty replies). Codex ran with `-a on-request -s workspace-write`. herdr was driven
only through the `p3x` socket. Fixtures: `tests/fixtures/herdr/agent-*-codex-*.json` and
`tests/fixtures/hooks/codex/payload-SessionStart-*-env.json`.

Summary:

| Check | Verdict |
|---|---|
| 1. AgentInfo carries `agent_session`; matches the hook `session_id` | PASS, but only when the hook env is correct. With the shared daemon it is absent (FAIL for the default setup). |
| 2. Stale `HERDR_*` reproduces; a fresh app-server changes it | Reproduced on 0.162.0. A fresh app-server does NOT fix it (isolated one verified). The user's managed daemon was not restarted: UNVERIFIED for that daemon. |
| 3. Two Codex panes, one cwd | PASS for "stay read-only": nothing in the payload or the herdr state separates them in the default setup. |

## Key finding: two Codex run modes

Codex runs hooks in an app-server process. Which process decides the hook environment.

- **Shared managed daemon (default).** A plain `codex ...` connects to the daemon
  (`~/.codex/app-server-daemon`, `app-server --listen unix:// --managed-daemon`). Hooks run with the
  environment the daemon was started with.
- **Embedded.** Codex prints the startup warning "Running without the shared background server: ... requires
  embedded mode" and runs the app-server in the TUI process. Triggers seen: `-c key=value`, and
  `--dangerously-bypass-hook-trust`. (The warning text also lists `--enable`, `--disable`, `--search`.) Plain
  `-m`, `-a`, `-s` stayed on the daemon. Hooks then get the pane's own environment.

## Check 1. `agent_session` in AgentInfo

**Evidence (embedded mode, pane `w1:p1`).** After the first prompt, `agent.get {"target":"w1:p1"}`
(`agent-info-codex-with-agent-session.json`):

```
"agent_session": {"source":"herdr:codex","agent":"codex","kind":"id","value":"01a11f87-cf06-79d1-a06c-ad853a2b34f1"}
```

The hook payloads for that pane carried `session_id: 01a11f87-cf06-79d1-a06c-ad853a2b34f1`. Exact match, in all
three runs where the env was right (embedded, and the fresh app-server pane below).

- Shape: object with `source` (`herdr:codex`), `agent`, `kind` (`id`), `value` (the Codex session id, a UUIDv7).
  Observed on `agent.list` and `agent.get`.
- Timing: absent right after `codex` starts. Codex fires `SessionStart` lazily, on the first prompt, not at
  startup (observed: no hook until the first `agent.prompt`). `agent_session` appeared after that and bumped
  `revision` (5 to 8 in the first run). A Codex pane that has not yet had a prompt has no hooks and no
  `agent_session`. That is harmless for permission requests (a request implies a session).
- Source of the value: herdr's own user hook `~/.codex/herdr-agent-state.sh` (SessionStart only). It reads
  `session_id` from the hook payload and calls `pane.report_agent_session` using **`HERDR_PANE_ID` and
  `HERDR_SOCKET_PATH` from the hook's environment**. So it has the same stale-env weakness as the shim.
- **Shared-daemon mode: no `agent_session` at all.** Pane `w1:p1` ran 2 full prompts with hooks firing
  (`agent-info-codex-shared-daemon-no-agent-session.json`). The herdr hook reported to the daemon's stale
  socket (the dead `spike` session), so the `p3x` pane never got a value.
- Not reproduced: `agent_session` for a pane resumed with `codex resume` (not tried).

**Verdict.** PASS for embedded and for any case where the hook env names the right pane. For the default
shared-daemon setup the claim "acd can bind by `agent_session`" is false: the field is missing.

## Check 2. Stale `HERDR_*` with a shared and a fresh app-server

**Reproduction (0.162.0, shared daemon).** Panes `w1:p1` and `w1:p2` in session `p3x`. Hook `_env` for every hook
event of both panes (`payload-SessionStart-shared-daemon-stale-env.json`):

```
HERDR_PANE_ID=w1:p2  HERDR_SESSION=spike  HERDR_SOCKET_PATH=/Users/.../sessions/spike/herdr.sock
```

That is the old `spike` session (dead), pane `w1:p2`. `ps eww` on the daemon (pid 46406, started
2026-10-08 22:06 by Codex 0.162.0) showed the same four variables, plus `HERDR_WORKSPACE_ID=w1`,
`HERDR_TAB_ID=w1:t1`, `HERDR_ENV=1`. The daemon pid, version and env are unchanged from P0's finding
(P0 saw 0.160.1). So the behaviour is not fixed in 0.162.

**Collision.** In `p3x` a real pane is also called `w1:p2`. Hooks from `w1:p1` claimed `HERDR_PANE_ID=w1:p2`, so
an acd that trusts the id alone would bind pane `w1:p1`'s permission request to the other Codex pane. Pane ids
are small and recycled across sessions, so this collision is likely, not exotic.

**Fresh app-server, isolated.** I did not restart the user's daemon (`ps`: it is the managed daemon with an
active control socket and a live Codex TUI, pid 53705, on another terminal). Codex does support a separate
instance without a different `CODEX_HOME`: `codex app-server --listen unix:///tmp/acp3/codex/app.sock` plus
`codex --remote unix:///tmp/acp3/codex/app.sock` in another pane. It reads credentials from `~/.codex` in place
(nothing copied). Setup: app-server started in pane `w1:p3`, TUI in pane `w1:p4`, one prompt in `w1:p4`.

- Hook `_env.HERDR_PANE_ID` was `w1:p3` (the pane that started the server), and `HERDR_SESSION=p3x`, correct
  socket. The conversation ran in `w1:p4`
  (`payload-SessionStart-fresh-app-server-other-pane-env.json`).
- herdr then attached the session id to the **wrong pane**: `agent.list` showed `w1:p3` with
  `agent_session.value = 01a11f8b-...` (the session that ran in `w1:p4`), and `w1:p4` had none
  (`agent-list-codex-fresh-app-server-misbound.json`). The `w1:p3` pane was only running the server process,
  and herdr detected it as `codex`.

**Verdict.** The reproduction passes. A fresh daemon does not change it: the hook env is the env of whoever
started the server, not of the TUI pane. Restarting the user's managed daemon would only make it inherit the
env of the pane that happens to start it next, so it would still be wrong for every other pane. Directly
observed on the managed daemon: not tried (UNVERIFIED), because it would interrupt the user's live Codex
session. The isolated server shows the mechanism and gives the same result.

Cause is not in the hook command. `_env` is whatever the server process has. There is no setting I found that
makes hooks inherit the TUI's env; embedded mode (`-c ...`) does it as a side effect.

## Check 3. Two Codex panes in one cwd

Panes `w1:p1` and `w1:p2`, both `cd /tmp/acp3/codex/d1`, shared-daemon mode, one prompt each.

Available binding data per pane:

| Source | `w1:p1` | `w1:p2` |
|---|---|---|
| hook `session_id` | `01a11f89-aad4-...` | `01a11f8a-5978-...` (distinct) |
| hook `cwd` | `/private/tmp/acp3/codex/d1` | same |
| hook `transcript_path` | own rollout file | own rollout file |
| hook `_env.HERDR_PANE_ID` | `w1:p2` (stale) | `w1:p2` (stale, same) |
| hook `_env.CODEX_THREAD_ID` | none | none |
| herdr `AgentInfo.agent_session` | none | none |
| herdr `cwd` | `/tmp/acp3/codex/d1` | `/private/tmp/acp3/codex/d1` (differs only by symlink) |
| TUI process args | no session id | no session id |

- `~/.codex/tui-thread-reference-capabilities/<session_id>` has empty files and no pid. `lsof` on the two TUI pids (99683, 1991)
  showed no open file that names the session id. No OS-level route from `session_id` to pane.
- Hooks from the two sessions interleave on one listener with identical env. Only `session_id` tells them apart,
  and nothing links a `session_id` to a pane.

**Verdict.** Refutes binding by `HERDR_PANE_ID`, `agent_session` and cwd in the default setup. Both hooks claim
the same wrong pane, both panes share a cwd, neither has `agent_session`. A permission request therefore could
not be tied to a pane except by screen content (the dialog command text), which two panes can share. The spec's
rule that ambiguous panes stay read-only is justified and, in the default setup, is the only safe outcome for
any cwd shared by 2+ Codex panes. Not tested: concurrent requests, or two embedded-mode panes (there the env and
`agent_session` are right, so binding would work).

## Other observations

- `SessionStart` fires at the first prompt, not at process start, and only `SessionStart`, `UserPromptSubmit`,
  `Stop` fired for the no-tool turns (as expected; no `PostToolUse`).
- `CLAUDE_CODE_ENTRYPOINT=sdk-ts` leaks into Codex hook env too (inherited from the tmux launcher). Irrelevant
  for Codex, but the shim should not read it.
- Project trust and hook trust prompts both appeared in daemon mode. Accepting them makes Codex write
  `[projects."<dir>"]` and `[hooks.state."<dir>/.codex/hooks.json:...]` entries to `~/.codex/config.toml`
  (the P0 precedent; a `-c`/bypass flag avoids it but forces embedded mode, which would have hidden the issue).
  I accepted them for `/private/tmp/acp3/codex/d1` and then removed exactly those 6 entries; the file is
  byte-identical to the pre-test copy.
- A stray `{}` POST hit port 47931 (another agent's listener) while I probed for a free port. It was my only
  contact with it; I then moved to 47961.

## Spec changes

1. **§6.1 step 2 and §6.3 "Resolution and binding" (Codex).** Replace the env-first order with: "For Codex, the
   hook environment is the environment of the app-server that runs the hook, usually the shared managed daemon
   (verified on 0.160.1 and 0.162.0). `HERDR_PANE_ID`, `HERDR_SOCKET_PATH` and `HERDR_SESSION` are untrusted
   and may name a dead session or another live pane. Ids repeat across sessions. Bind only when all hold:
   (a) `HERDR_SOCKET_PATH` equals acd's herdr socket, (b) the pane's `AgentInfo.agent_session.value` equals the
   hook `session_id`. Otherwise the hook is unbound."
2. **§6.3** Add: "`agent_session` is the only strong key and is absent for Codex in shared-daemon mode. Without
   it, acd may bind by cwd plus dialog fingerprint only when exactly one Codex pane is in that cwd (compare
   after resolving symlinks: herdr reports `/tmp/...`, Codex reports `/private/tmp/...`). With 2+ Codex panes in
   one cwd, every request stays read-only." Keep the existing ambiguity rule and cite this evidence.
3. **§6.1/§6.3 note.** `SessionStart` fires on the first prompt, so a fresh Codex pane has no `agent_session`
   until then. An unbound idle pane is expected.
4. **§5 / install.** `acd hooks install` for Codex must warn: hooks are bound only when the user runs Codex in
   embedded mode or starts the managed daemon from a known pane. A restart of the daemon is not a fix (the env
   follows whoever starts it). Optionally recommend upstream: report that herdr's integration hook and acd both
   depend on the daemon's env (the herdr hook can mis-attach a session to the pane that started the server, as
   in check 2).
5. **§11 gate 4.** Mark the Codex part: AgentInfo `agent_session` shape `{source,agent,kind:"id",value}` verified
   and equal to the hook `session_id`; env staleness reproduced on 0.162.0; fresh isolated server does not
   cure it; managed-daemon restart UNVERIFIED.
