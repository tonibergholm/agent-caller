# P0 verification checks for spec §11

Date: 2026-10-07
Spec: `docs/superpowers/specs/2026-10-07-agent-inbox-design.md` (revision 3), §11 items 2–9
Versions: herdr 0.9.3 (protocol 22), Claude Code 2.1.292, Codex CLI 0.160.1, T3 Code at
`611132c` (source only).

Method common to all live checks: an isolated herdr session `p0` inside a detached tmux
session, project-local hooks in scratch dirs under `/tmp/acp0/`, and a throwaway Python
listener (`python3 -I`) that logged every hook payload and could hold, allow or deny. Claude
ran in manual permission mode. Codex ran with `-a on-request -s workspace-write`. Fixtures are
in `tests/fixtures/{hooks/claude,hooks/codex,herdr}/`. Item 1 and item 10 are not in scope.

Summary of results that change the spec:

| Item | Result |
|---|---|
| 2 | Deny works. "Always allow" persists only through `addRules` with destination `localSettings`, `projectSettings` or `userSettings`. The documented shape is ignored. |
| 3 | T3 contract settled from source. Token goes in an `Authorization: Bearer` header or a `wsTicket` query param. Stale responses are rejected. |
| 4 | No mark-seen method exists. `agent.focus` is the only documented way. |
| 5 | Codex dialog appears 35 / 75 / 118 ms (min / median / max) after the hook returns. The 3 s wait can drop to about 1 s. |
| 6 | Deny wins over allow on both agents. The held Claude hook is left open and ignored. |
| 7 | `state_change_seq` is one server-wide counter. Events do not carry it. `pane.agent_status_changed` needs a `pane_id`. |
| 8 | Killing a command hook leaves a usable dialog. A terminal answer does NOT close a command hook's connection (it does for an `http` hook). |
| 9 | Yes: `~/.claude/sessions/<pid>.json` lists live sessions. |

Two findings outside the numbered items matter just as much and are recorded under
"Additional findings".

## Item 2. Claude `PermissionRequest` decisions

**Question.** What do the allow and deny payloads and replies look like? Does deny actually
deny? Is there a field that persists "always allow"?

**Method.** The listener held the hook. A reply file released it with a chosen body. Commands
were `touch` files under `/tmp/acp0` and `~/`. The docs at
`https://code.claude.com/docs/en/hooks` were read for `updatedPermissions`. Several shapes
were tried, and persistence was checked by re-running the same command and watching whether the
hook fired again.

**Evidence.**

- Payload (fixture `hooks/claude/payload-PermissionRequest-Bash.json`): `session_id`,
  `transcript_path`, `cwd`, `prompt_id`, `permission_mode`, `effort`, `hook_event_name`,
  `tool_name`, `tool_input{command,description}`, `permission_suggestions[]`. In this run the
  suggestions were `{"type":"addDirectories","directories":["/tmp/acp0"],"destination":"session"}`
  and `{"type":"setMode","mode":"acceptEdits","destination":"session"}`.
- Allow reply (`response-allow.json`): the command ran. Claude printed "Allowed by
  PermissionRequest hook".
- Deny reply (`response-deny.json`): the file was not created. Claude printed "Denied by
  PermissionRequest hook" and relayed the message to the model.
- `updatedPermissions` in the shape the docs show
  (`{"type":"allow","rules":["Bash(npm run *)"],"behavior":"auto","destination":"project_settings"}`):
  **ignored.** The allow was not applied, the dialog stayed up, and Notification fired. The
  hook output was treated as invalid and fell back to the dialog (fixture
  `response-allow-docs-shape-IGNORED.json`).
- `addRules` with `destination: "session"` (`response-allow-addRules-session-NOT-PERSISTED.json`):
  the allow worked, but the same command prompted again.
- `addDirectories` with `destination: "session"` (the suggestion round-tripped): the allow
  worked, but the next command in that directory prompted again.
- `addRules` with `destination: "localSettings"` (`response-allow-always-localSettings.json`):
  **persisted.** Claude wrote `{"permissions":{"allow":["Bash(touch /tmp/acp0/*)"]}}` to
  `.claude/settings.local.json`, and the next matching command did not fire the hook.
- `addRules` with `destination: "projectSettings"`: persisted into `.claude/settings.json`.
  Claude also reformatted the whole file (indent 1 to indent 2).
- A shape that works:
  `{"type":"addRules","rules":[{"toolName":"Bash","ruleContent":"touch /tmp/acp0/*"}],"behavior":"allow","destination":"localSettings"}`.
  `ruleContent` is the pattern inside `Bash(...)`.

**Result.** The spec's allow and deny envelopes are correct. "Yes, always" can be offered
through a hook, but only by writing a rule to a settings file (`localSettings` is the least
invasive). The `permission_suggestions` entries are mostly not rules (here, a directory and a
mode), so acd would have to build the rule itself.

**Proposed spec change.**
- §6.2 "Permission requests" step 1: replace the `allow_always` bullet with: "`allow_always`
  "Yes, always" is offered when the request has a `Bash`, `Edit` or `Write` tool. acd replies
  `allow` plus `updatedPermissions: [{"type":"addRules","rules":[{"toolName":<tool>,"ruleContent":<pattern>}],"behavior":"allow","destination":"localSettings"}]`.
  The `destination: session` and `addDirectories` forms do not persist, and the shape shown in
  the Claude docs (`type: allow`, string rules) is ignored. This writes to the user's project
  `.claude/settings.local.json`, so the client must show the exact rule before sending."
- §6.2 step 3: delete "(the deny shape is pending verification as a recorded fixture, §11
  item 2)". The fixture is `tests/fixtures/hooks/claude/response-deny.json`.
- Add to §5.1 or §6.2: a malformed `decision` makes Claude fall back to the dialog (fail open).

## Item 3. T3 contract (source reading only)

**Question.** WebSocket URL and token presentation, decision literals, pending request shape,
question and answer shape, stale and duplicate rejection, and replay on reconnect.

**Method.** Read `packages/client-runtime/src/{rpc,connection,authorization}`,
`packages/contracts/src/{orchestrationV2,providerPolicy,auth,environmentHttp,clientRpcPermissions}.ts`
and `apps/server/src/{ws.ts,auth/*,orchestration-v2/Orchestrator.ts}`. Nothing was run against
the T3 server and no token was issued.

**Evidence and result.**

1. **URL and token.**
   - Path: `ws(s)://<host>:<port>/ws`. The server rejects with HTTP 426 unless the URL has
     `orchestrationProtocol=2` (`ORCHESTRATION_PROTOCOL_QUERY_PARAM`, `ws.ts:604`,
     `contracts/src/environment.ts:13`).
   - Normal client flow: `POST /api/auth/websocket-ticket` with `Authorization: Bearer <token>`
     returns `{ticket, expiresAt}`. The client then connects to
     `/ws?orchestrationProtocol=2&wsTicket=<ticket>`
     (`client-runtime/src/authorization/remote.ts:161,201`). The ticket is a signed token with
     a 5 minute TTL (`SessionStore.ts:430`). It is not marked single-use in the code read.
   - The upgrade authenticator (`EnvironmentAuth.authenticateWebSocketUpgrade`,
     `EnvironmentAuth.ts:1173`) checks `wsTicket` first, then falls back to the request
     credentials: cookie, then `Authorization: Bearer`, then DPoP. So a plain
     `Authorization: Bearer` header on the upgrade request should also work. **Needs live
     check.**
   - Optional `clientSurface`, `clientAppVersion` and similar params are attribution only.
   - Framing: effect/rpc over WebSocket with `RpcSerialization.layerJson` (`rpc/session.ts:211`).
     The spec's "hand-written Rust types" must also implement the effect-rpc request, chunk and
     exit envelope. The exact envelope bytes **need a live check or a read of `effect/rpc`**.
2. **Decision literals** (`providerPolicy.ts:50`): `"accept"`, `"acceptForSession"`,
   `"acceptAlways"`, `"decline"`, `"cancel"`. Requests can carry `options[]` of
   `{decision, label, warning?}` (approval turn item). `ProviderRequestKind`: `command`,
   `file-read`, `file-change`, `mcp-elicitation`, `permission`. Runtime request kind adds
   `dynamic_tool_call`, `user_input`, `auth_refresh`.
3. **Pending request shape.**
   - Shell (`subscribeShell`): each thread has
     `pendingRuntimeRequest: {id, kind, createdAt} | null` and
     `status` in `idle|preparing|queued|starting|running|waiting|completed|interrupted|failed|cancelled|rolled_back`
     (`orchestrationV2.ts:1816,1870`). The shell alone is enough to know a thread is waiting
     and which request id.
   - Thread projection (`subscribeThread` / `getThreadProjection`): `runtimeRequests[]` of
     `{id,nodeId,providerTurnId,nativeRequestRef,kind,status: pending|resolved|expired|cancelled,responseCapability,createdAt,resolvedAt,decision?,answers?}`.
     `responseCapability` is `{type:"live",providerSessionId}`, `{type:"message"}` or
     `{type:"not_resumable",reason}`.
   - The human-readable detail is in `turnItems` (matched by `requestId`): `approval_request`
     `{requestId, requestKind, prompt?, appName?, options?}` and `user_input_request`
     `{requestId, questions[], questionAnswer?, responseMode?: "message"}`. A command string is
     not in the request itself. `prompt` is the only text. **How `prompt` is filled for a
     `command` request needs a live check.**
4. **Question and answer shape.**
   - Question: `{id, header, question, options:[{label, description, value?}], multiSelect?, allowCustomAnswer?, required?}`.
     A request has an array of questions, so multiple questions are native.
   - Answer: `answers: Record<questionId, string | string[]>` (built in
     `apps/web/src/pendingUserInput.ts`). A single select sends `option.value ?? option.label`.
     A multi select sends an array. A custom answer is a plain string and outranks selected
     options. `attachmentsByQuestionId` is optional.
   - `responseCapability.type: "message"` (async questions): the answer is turned into a new
     user message and every question with `required !== false` must have a non-empty string.
     An array answer fails that check (`typeof answer !== "string"`).
5. **Command.** `orchestration.dispatchCommand` with
   `{type:"runtime-request.respond", commandId, threadId, requestId, decision? , answers?, attachmentsByQuestionId?}`.
   `thread.user-input.dismiss` cancels a `message`-mode question.
6. **Stale and duplicate answers: rejected.** `dispatchRuntimeRequestRespond`
   (`Orchestrator.ts:7038`) fails with `Runtime request <id> is <status>.` when the status is
   not `pending`, and with "was not found" when it is missing. Dispatch for a thread runs
   under `threadDispatch.withLock` (`Orchestrator.ts:10605`), so two racing responses are
   serialized and the second sees `resolved`. A repeated `commandId` returns the stored
   receipt instead of re-running (`Orchestrator.ts:10407`). acd must choose a stable
   `commandId` per claim, and treat the receipt as success. A rejected command is remembered
   (`OrchestratorCommandPreviouslyRejectedError`).
7. **Subscriptions and reconnect.** `subscribeShell{afterSequence?, requestCompletionMarker?}`
   and `subscribeThread{threadId, afterSequence?, requestCompletionMarker?, acceptBoundedSnapshot?}`.
   Without `afterSequence` the stream starts with a full `snapshot` item. With it, the server
   replays events after that sequence, deduped by sequence on the client, then goes live.
   `synchronized` marks the end of catch-up. Shell items carry `sequence`. Thread events carry
   `sequence`. Unknown thread events arrive as `unknown-event`. How far back the server can
   replay (retention) **needs a live check**. The client session does not auto-retry
   (`retryPolicy: recurs(0)`), so reconnect is the caller's job.
8. **Scopes.** `orchestration:read` and `orchestration:operate` exist (`auth.ts:82`). Which
   scope each orchestration RPC needs is enforced by `RpcScopeAuthorization`. **Needs live
   check** that `dispatchCommand` needs `operate` and the subscriptions need `read`.

**Proposed spec change.**
- §6.5 "Connection": "URL `ws://<host>:<port>/ws?orchestrationProtocol=2&wsTicket=<ticket>`.
  acd obtains `<ticket>` with `POST /api/auth/websocket-ticket` and `Authorization: Bearer`
  (5 minute TTL, request a new one per connect). Framing is effect/rpc JSON. A direct
  `Authorization: Bearer` header on the upgrade is expected to work (live check)."
- §6.5 "Requests": "A waiting thread's shell entry carries `pendingRuntimeRequest {id, kind}`.
  acd reads `turnItems` of type `approval_request` or `user_input_request` (same `requestId`)
  from `subscribeThread` for the detail. Approval options are the request's `options[].decision`,
  falling back to `accept`, `acceptForSession`, `decline`. Map to effects: `accept` is allow,
  `acceptAlways` and `acceptForSession` are allow_always, `decline` and `cancel` are deny."
- §6.5 "Answers": "`answers` is `Record<questionId, string | string[]>`. Use
  `option.value ?? option.label`. `message`-mode questions need string answers. Stale answers
  are rejected by T3 (`Runtime request … is resolved`) and dispatch is serialized per thread, so
  the pre-dispatch projection check is not required. Use one `commandId` per claim."
- §6.5 "Contract": add `afterSequence` resume for shell and thread subscriptions.

## Item 4. herdr seen state

**Question.** Can the socket API mark a pane seen?

**Method.** Read the bundled schema (`herdr api schema --json`, also fetched from
`docs/next/api/herdr-api.schema.json`), `herdr --skill`, and the full request method list. Then
called `agent.focus` on a live agent.

**Evidence.**
- The request methods are `agent.{explain,focus,get,list,prompt,read,rename,send_keys,start,wait,view.set,view.clear}`,
  `pane.*`, and so on. There is no `mark_seen`, `agent.seen` or similar.
- `seen` appears only as an agent-view field (`AgentViewBuiltinField`, a sort key). Agent
  objects have no `seen` field.
- `herdr --skill` says: "The CLI/API uses the server's seen state to distinguish [idle and
  done]; explicit focus commands mark the target seen, while reads do not. Each TUI client
  tracks viewed completions independently."
- `agent.focus` returned ok. Focus also moves the herdr UI focus.
- I could not reproduce the `done` state in this setup. Agents went `working` then `idle`
  in unfocused and zoomed-away panes, after both `agent prompt` and raw `pane send-text`. So
  whether `agent.focus` flips `done` to `idle` is **unverified**.

**Result.** No dedicated mark-seen. `agent.focus` is documented as marking seen but has a UI
side effect.

**Proposed spec change.** §6.4 "Seen state": "herdr has no mark-seen method. acd keeps its own
seen flag per agent for `agent.mark_seen`, and does not call `agent.focus`, because focus moves
the user's herdr UI. herdr's `done` state is shown as-is until the user focuses the pane."

## Item 5. Codex dialog timing

**Question.** How long after a `PermissionRequest` hook returns does the approval dialog show
in `herdr agent read --source detection`?

**Method.** Codex hook = the listener replying empty at once. A script sent a prompt that
needed approval (`touch ~/acp0_test_t5_N.txt`), polled `agent.read` over the socket every
~10 ms, and compared the first poll containing "Would you like to run" with the shim's
end-of-run timestamp (`out/shimend.log`). Six runs, `esc` between runs.

**Evidence.** Delay from hook end to dialog in detection: 74, 89, 118, 45, 35, 77 ms.
Min 35 ms, median 75 ms, max 118 ms. The hook end is the shim script's last line, so process
exit adds a few ms. Separately, the model took 6–16 s to reach the tool call.

**Result.** The dialog appears within about 120 ms after the hook returns.

**Proposed spec change.** §6.3 "Answering": "acd waits up to 1 s (measured max 118 ms over 6
runs) for the dialog fingerprint before it reports the request as claimable-failed." Keep the
`request_not_ready` behavior.

## Item 6. Coexisting permission hooks

**Question.** With a second `PermissionRequest` hook that allows or denies, which decision
wins, and what happens to the acd-like hook?

**Method.** Claude: three hooks in one matcher group, the held shim plus `fixed.py allow`
(dir `claude2`) or `fixed.py deny` (dir `claude3`). Codex: the immediate-empty shim plus
`fixed.py allow` (`codex2`), and the empty shim plus deny plus allow (`codex3`). Each run
asked for a command that needs approval.

**Evidence.**
- Claude, held + allow: the command ran, no dialog. The held shim process stayed alive and the
  listener saw no close. A later reply was ignored. Claude does not kill or time-out the
  loser.
- Claude, held + deny: the command did not run. Claude reported "Denied by second hook".
- Codex, empty + allow: the file was created, no dialog. Hooks were invoked within 1 ms of each
  other (concurrent).
- Codex, empty + deny + allow: not created. The screen showed "Blocked by hook / Denied by
  second hook". Both fixed hooks were invoked.

**Result.** Deny wins over allow. Any decisive hook beats an empty one. Hooks run
concurrently. For Claude the held acd hook is left open and ignored, with no close signal.

**Proposed spec change.** §6.1 "Coexisting permission hooks": replace the last sentence with:
"Verified: any decisive hook beats an empty reply, and deny beats allow. A losing held Claude
hook gets no close signal and its process lingers until acd replies or `permission_hold`
expires, so acd resolves such requests through reconciliation (`PostToolUse`, `Stop`, or the
fingerprint leaving the screen). acd should answer a lingering held hook with an empty reply
when it learns the request ended."

## Item 7. herdr sequencing

**Question.** What does `state_change_seq` cover, what is the order between `events.subscribe`
and `agent.list`, and can gaps be detected?

**Method.** A Python NDJSON client on `~/.config/herdr/sessions/p0/herdr.sock`
(`bin/hc.py`). Subscribed, produced status changes in two agents, and compared stream events
with `agent.list` / `agent.get`.

**Evidence.**
- Socket protocol: one request per connection, `{"id","method","params"}` as one JSON line.
  A second request on the same connection hit a broken pipe, so non-subscription calls need a
  new connection each. `events.subscribe` keeps its connection open and replies
  `{"result":{"type":"subscription_started"}}`.
- **Subscription names are dotted:** `pane.agent_status_changed`, `pane.agent_detected`,
  `pane.closed`, `pane.created`. The spec uses underscored names, which the server rejects
  ("unknown variant `pane_agent_status_changed`").
- **`pane.agent_status_changed` requires `pane_id`** (and takes an optional `agent_status`
  filter). Without it the server answered "missing field `pane_id`". There is no
  all-panes status subscription. acd must subscribe per pane and also watch
  `pane.created`, `pane.agent_detected` and `pane.closed`.
- Stream frame: `{"event":"pane.agent_status_changed","data":{"agent","agent_status","pane_id","workspace_id"}}`.
  **No `state_change_seq`, no title.** The schema's `PaneAgentStatusChangedEvent` has none.
  Events seen for create and close: `pane.created` with `data.pane`, and `pane_closed` (note
  the underscore) with `{pane_id, type:"pane_closed", workspace_id}`. The stream schema lists
  only `pane.output_matched`, `pane.agent_status_changed` and `pane.scroll_changed` as kinds,
  so the other frame names are not schema-guaranteed.
- `state_change_seq` appears in `agent.list`, `agent.get` and `agent.start` results with
  `completion_seq` and `revision`. Observed: cx1 = 90 and cl1 = 85 before. One Codex change
  (blocked to idle) set cx1 to 91. Then two Claude changes (working, idle) set cl1 to 92
  and 93, and two more Claude runs gave 94-95 and 96-97. Values interleave across agents,
  so **it is one server-wide counter bumped on every agent status change**, not per pane.
- No `events_lost` or overflow message exists in the schema or in anything observed.

**Result.** Spec §6.4 step 3 ("apply buffered events whose `state_change_seq` is newer than
the list entry") is not implementable: events carry no sequence. The counter is global, so a
per-pane gap cannot be detected from events. A change is detectable only after the fact, by
seeing a pane's `state_change_seq` in `agent.list` jump past the last value acd saw without an
event for that pane.

**Proposed spec change.** §6.4 "Sync" replace steps 1–4 with:
1. Open one subscription connection with `pane.created`, `pane.closed`, `pane.agent_detected`,
   and one `pane.agent_status_changed{pane_id}` per known pane. Add a per-pane subscription
   when `pane.created` or `pane.agent_detected` arrives.
2. Call `agent.list` (new connection) and build state from it.
3. Treat every stream event as a hint: on any event, call `agent.get` for that pane and
   replace the state with the result. This makes ordering between the stream and the list
   irrelevant.
4. Reconcile with `agent.list` on reconnect, every 5 s while any agent is `blocked`, and every
   30 s otherwise. A pane whose `state_change_seq` rose without an event is a missed change.
   There is no `events_lost` signal, so a dropped connection always triggers a full resync.

Also fix the event names in §6.4 to the dotted forms.

## Item 8. Shim lifecycle (Claude)

**Question.** (a) Kill the hook process during a hold. (b) Answer at the terminal and by hook
within about 100 ms. (c) Restart the listener mid-hold.

**Method.** Hook = `command` type shim that POSTs to the listener and holds. Answers sent
with `herdr agent send-keys cl1 1` (terminal) and a reply file (hook).

**Evidence.**
- (a) `kill -9` of the shim: the listener logged `hold_conn_closed` within 0.2 s. The dialog
  stayed, `agent_status` stayed `blocked`, and `send-keys 1` ran the command. Fail open works.
- **(b) Terminal answer with a `command` hook.** The listener never saw the connection close
  and the shim process stayed alive (`ps` state `Ss`) until released. Claude proceeded
  (`PostToolUse` arrived 90 ms after the key). A later `allow` reply was ignored and the shim
  exited quietly. So a `command` hook gives no "answered elsewhere" signal. This contradicts
  the landscape spike's "Claude closes the hook's HTTP connection": that was true for an
  `http` hook. A `type: "http"` hook (dir `claude4`) did close its connection as soon as the
  key was pressed (`hold_conn_closed` logged).
- (b) Race, 4 runs, `echo` appended to a file as the execution counter (key and hook reply
  about 50 ms apart): key first with allow: 1 execution. Hook first with allow: 1. Key first
  with deny: 1 execution (the terminal won). Hook first with deny: 0 executions. Exactly one
  outcome every time.
- **Hazard.** In the hook-first deny run the late `1` keypress was typed into Claude's prompt
  box (`❯ 1`) because the dialog had already gone. This is the invariant 3 risk made concrete.
  The guard (re-read screen, compare the fingerprint, send one key) narrows it but cannot
  close it.
- (c) Listener killed mid-hold: the shim failed (`urlopen` error), printed nothing and
  exited 0. The dialog stayed and `blocked` persisted. After the listener restarted, `1`
  answered the dialog normally.

**Result.** (a) and (c) are as the spec assumes. (b) holds for "exactly one outcome". Its
detection premise (closed connection) is wrong for command hooks.

**Proposed spec change.**
- §6.2 step 5: replace "The spike showed this case arrives as a closed connection" with:
  "With a `command` hook (the only type Codex has, and what the shim is) a terminal answer
  does not close the connection and the shim stays alive. acd detects a terminal answer from
  `PostToolUse`/`Stop`, or from the fingerprint leaving the screen (herdr-bound), and then
  replies empty to the held hook so the shim exits. A killed shim or restarted acd does close
  the connection, so reconcile as written." Alternatively, offer an `http`-type hook for
  Claude, which does close on terminal answer, at the cost of losing the herdr env vars (the
  http payload has no `_env`, so binding must use `session_id`).
- §5.1 "Hooks-only agents": remove the claim that a closed connection means "answered
  elsewhere". For hooks-only Claude with a command hook, use `PostToolUse`/`Stop`, with the
  30 s `uncertain` fallback.
- §4 invariant 3 / §12: note that a keystroke sent after the dialog closes lands in the agent's
  input box. The post-send confirmation must check the prompt line and warn the user.

## Item 9. Hooks-only Claude discovery

**Question.** Can already-running Claude sessions outside herdr be found without a hook?

**Method.** Looked at `ps` and `~/.claude`.

**Evidence.** `~/.claude/sessions/<pid>.json` exists for each live interactive session. Fields
seen: `pid`, `sessionId`, `cwd`, `startedAt`, `procStart` (process start time string),
`version`, `kind` (`interactive`), `entrypoint` (`sdk-ts`, `cli`), `name`, `status`
(`busy` seen), `updatedAt`, `statusUpdatedAt`, `messagingSocketPath`. Files for my own
test sessions were gone after they exited. The directory also holds `<pid>.<hash>.key`
files, which are secrets and must not be read. `ps` shows the `claude` processes but not the
session id. Transcripts under `~/.claude/projects/<cwd-slug>/<sessionId>.jsonl` carry the same
`sessionId`.

**Result.** Yes. The reliable signal is the `~/.claude/sessions/*.json` registry. Validate each
entry by `kill -0 <pid>` and by matching `procStart` against the process start time, which
guards against pid reuse and crashed sessions. Other values of `status` (for example waiting on
a permission) **need a live check**. The file format is undocumented and may change, so this
must be an optional source with `degraded` on parse errors.

**Proposed spec change.** §11 item 9: replace with "Resolved: acd scans
`~/.claude/sessions/*.json` (never the `.key` files) at startup and every 30 s to create
hooks-only agents with `kind`, `cwd`, `name` and `status`, validated by pid and `procStart`.
Entries with `entrypoint` in the ignore list are skipped." Add to §6.2 "Binding" that a
hooks-only agent can exist before its first hook.

## Additional findings

1. **Codex hooks can carry a stale herdr environment.** Hook payloads from Codex in pane
   `w1:p7` of session `p0` carried `HERDR_PANE_ID=w1:p2` and
   `HERDR_SOCKET_PATH=.../sessions/spike/herdr.sock`, which is the earlier spike's session.
   Codex 0.160 runs hooks inside a shared managed `codex app-server` daemon
   (`~/.codex/app-server-daemon`, started earlier), whose environment is not the pane's.
   The landscape note "hook processes inherit HERDR_PANE_ID for both Claude and Codex" is
   unreliable for Codex. Claude hooks always carried the right pane. Spec change, §6.1 step 2
   and §6.3 "Resolution and binding": for Codex, do not trust `HERDR_PANE_ID` or
   `HERDR_SOCKET_PATH`. Bind by `session_id` (herdr agent session, once reported) or by
   `cwd` plus the matching dialog fingerprint, and use the env only when it names a pane
   whose agent matches. This was not investigated further (for example with the daemon
   restarted). Mark it as needing a follow-up. I did not touch the daemon.
2. **`CLAUDE_CODE_ENTRYPOINT` is inherited, not set per session.** Claude hooks reported
   `sdk-ts` in a pane whose shell had inherited that variable from the process that started
   tmux. After `unset CLAUDE_CODE_ENTRYPOINT`, a terminal session reported `cli`. With
   `sdk-ts` inherited, Claude also skipped the folder-trust prompt. Spec change, §6.2
   "Filter": the entrypoint ignore list can drop a real terminal session that was launched
