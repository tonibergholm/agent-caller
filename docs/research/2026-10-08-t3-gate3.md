# Spec §11 gate 3: T3 Code, live check

Date: 2026-10-08. T3 `v0.0.46-nightly.20261008.2801` (orchestration protocol
2, effect 4.0.1). Fixtures: `tests/fixtures/t3/` (76 files; tokens, tickets
and home paths redacted).

## Method

- **Server.** A throwaway headless server, isolated from the desktop app:
  `t3 serve --base-dir /tmp/acp4/t3home --port 47990 --host 127.0.0.1 --no-browser /tmp/acp4/proj`,
  with `T3CODE_HOME=/tmp/acp4/t3home` for every CLI call.
- **Project.** `/tmp/acp4/proj`, a git repo with one file.
- **Tokens.** Three, issued with `t3 auth session issue`:
  - `rw`: `orchestration:read` and `orchestration:operate`;
  - `ro`: `orchestration:read`;
  - `diag`: `diagnostics:read`.
- **Client.** A Python stdlib WebSocket client that logged every frame.
- **Source.** Read from the bundled `app.asar`. Claims below are marked
  "live" (observed) or "source" (read only).
- **Agent runs.**
  - Claude, `approval-required`:
    - a Bash approval, accepted;
    - an AskUserQuestion, answered;
    - one approval left pending through a server restart.
  - Codex: one approval, declined.

## 1. Auth (live)

**Ticket request.** `POST /api/auth/websocket-ticket` with
`Authorization: Bearer <token>` and no body returns
`200 {"ticket":"<192 chars>","expiresAt":"<now+5min>"}`.

- The ticket can be reused while it is valid.
- An expired ticket gets `401 {"_tag":"EnvironmentAuthInvalidError","code":"auth_invalid","reason":"invalid_credential",...}`.
- The ticket is checked only at the upgrade. An open socket keeps working
  after its ticket expires.
- A missing credential gives `missing_credential`; a bad token gives
  `invalid_credential`.
- The ticket endpoint needs no particular scope.

**URL.** `ws://host:port/ws?orchestrationProtocol=2&wsTicket=<ticket>`.

- A missing or wrong protocol parameter gets
  `426 {"code":"orchestration_protocol_incompatible",...,"orchestrationProtocolVersion":2}`.
- The header `x-t3-orchestration-protocol` is also accepted (source).

**Bearer header on the upgrade.** An `Authorization: Bearer <token>` header
on the WebSocket upgrade, with no `wsTicket`, is also accepted.

**Token lifetime.** CLI tokens default to 30 days (`--ttl`).

## 2. Envelope (live)

Each WebSocket text frame is one JSON object. The source also accepts
arrays.

- **Request:** `{"_tag":"Request","id":"1","tag":"orchestration.subscribeShell","payload":{...},"headers":[]}`
- **Chunk:** `{"_tag":"Chunk","requestId":"1","values":[...]}`
- **Ack, required.** The client must answer every Chunk with
  `{"_tag":"Ack","requestId":"1"}`. Without acks, only the first chunk
  arrives.
- **Success:** `{"_tag":"Exit","requestId":"1","exit":{"_tag":"Success","value":{...}}}`
- **Failure:** `{"_tag":"Exit","requestId":"1","exit":{"_tag":"Failure","cause":[...]}}`.
  Each cause is one of:
  - `{"_tag":"Fail","error":{"_tag":<TypedError>,...}}`;
  - `{"_tag":"Die","defect":"<text>"}`, for schema errors, unknown tags and
    bad literals;
  - `{"_tag":"Interrupt","fiberId":n}`.
- **Client interrupt:** `{"_tag":"Interrupt","requestId":"1"}`.
- **Keepalive:** `{"_tag":"Ping"}` gets `{"_tag":"Pong"}`. The server sent no
  pings in 9.4 minutes, and idle sockets stayed open.
- **Server shutdown:** sockets are closed with code 1001.

## 3. Subscriptions

Methods: `orchestration.subscribeShell`, `orchestration.subscribeThread`
and `orchestration.dispatchCommand`.

**Params.**

- Shell: `{afterSequence?, requestCompletionMarker?}`.
- Thread: `{threadId, afterSequence?, requestCompletionMarker?, acceptBoundedSnapshot?}`.

**Shell items.**

- `snapshot {snapshot:{schemaVersion, snapshotSequence, projects, threads, archivedThreads}, resolvedRepositoryIdentityRoots?}`
- `synchronized`
- `project.updated` and `project.removed`
- `thread.updated {sequence, location, thread}`
- `thread.removed {sequence, location, threadId}`

**Project-only snapshots.** A snapshot that carries
`resolvedRepositoryIdentityRoots` holds project metadata with `threads: []`.
It arrives after the full snapshot, on every resume, and mid-stream.
Treating it as a full replace wipes every thread.

**Thread items.**

- `snapshot {snapshotSequence, projection}`, where `projection` holds
  `thread`, `runs`, `providerThreads`, `runtimeRequests`, `turnItems`,
  `messages`, ...
- `synchronized`
- `event {sequence, event:{type, payload,...}}`

**Sequences.** Shell and thread events share one global sequence. The shell
skips unchanged thread updates, so it has gaps.

**Statuses observed:** `idle`, `starting`, `running`, `waiting`,
`completed`, `cancelled`.

**A pending request (live).** While an approval or question was pending, the
shell entry was:

- `status:"running"`, `activityRunStatus:"running"`;
- `pendingRuntimeRequest:{id, kind:"command"|"user_input", createdAt}`.

`waiting` appeared only after the answer, for 140–200 ms with no request,
and then became `completed`. The source calls it a "post-terminal drain".

**Approval item.** In `turnItems`, `type:"approval_request"`:

- fields: `requestId`, `requestKind:"command"`, `prompt`,
  `nativeItemRef:{driver, nativeId}`, `status:"waiting"`;
- no `options` from either provider.

**`runtimeRequests[]`.** An entry has
`{id, kind, status:"pending", responseCapability:{type:"live", providerSessionId}, nativeRequestRef, createdAt, resolvedAt}`.
On resolution it becomes `status:"resolved"`, with `decision` or `answers`.

**Question item.** In `turnItems`, `type:"user_input_request"`:

- `questions:[{id, header, question, options:[{label, description}], multiSelect:false}]`;
- for Claude, `id` is the question text, and options have no `value`;
- after the answer, `questionAnswer:{requestId, questionTextById, answers, attachmentsByQuestionId}`.

## 4. Resume

**Live.**

- Shell `afterSequence:N` gives:
  1. a project-only snapshot;
  2. the events after `N`;
  3. `synchronized`.
- Thread `afterSequence:N` gives the events after `N`, then `synchronized`.
- An `afterSequence` past the head gives a full snapshot.
- A negative value gives `Die`.
- There is **no** "expired" or "not resumable" error. The server falls back
  to a snapshot.

**Fallback thresholds (source).**

- Shell: a gap of more than 1000, or the payload budget exceeded.
- Thread: more than 128 events, more than 1 MiB, or a create event in the
  range.

**Client rules.**

- Replace state on any snapshot that does not carry
  `resolvedRepositoryIdentityRoots`.
- Drop events at or below the cursor.

**After a server restart (live).** The pending Claude request had become:

- `status:"cancelled"`;
- `responseCapability:{type:"not_resumable", reason:"Provider session was closed before this runtime request was resolved."}`.

The run and the shell went `cancelled`, with `pendingRuntimeRequest:null`.
Responding then gave `Runtime request … is cancelled.`

## 5. Scopes

**Required scopes (source, `RPC_REQUIRED_SCOPES`).**

- `orchestration:read`: `subscribeShell`, `subscribeThread`,
  `getThreadProjection`, `server.getConfig`.
- `orchestration:operate`: `dispatchCommand`, `launchThread`.

**Missing scope (live).** The error is
`Fail {"_tag":"EnvironmentAuthorizationError","message":"The authenticated token is missing required scope: orchestration:operate.","requiredScope":...}`.
The payload is decoded first, so a malformed payload gives `Die` even when
the scope is missing.

## 6. dispatchCommand (live)

**Ack.** A successful command returns `{"sequence":N}`.

**`message.dispatch`.**

```json
{"type":"message.dispatch","createdBy":"user","creationSource":"web","commandId":"<uuid>","threadId":"<id>","messageId":"<uuid>","text":"...","attachments":[],"deliveryIntent":"auto","dispatchMode":{"type":"start_immediately"}}
```

- `titleSeed` is optional.
- A message sent while a run is active is queued, not refused (source).

**`runtime-request.respond`.**

- With a decision: `{"type":"runtime-request.respond","commandId","threadId","requestId","decision":"accept"}`.
- With answers: `{...,"answers":{"<questionId>":"<value>"}}`.
- The allowed decisions are `accept`, `acceptForSession`, `acceptAlways`,
  `decline` and `cancel`. Any other value gives `Die`.

**A second respond with a new `commandId`.** It fails with
`Fail {"_tag":"OrchestrationV2DispatchCommandError",...,"message":"Runtime request <id> is resolved."}`.
The other messages are `… is cancelled.` and `… was not found.`

**`commandId` reuse.**

- The same id returns the stored receipt, even when the payload differs. T3
  does not check for a mismatch.
- A previously rejected id stays rejected.

## 7. Prompt and title

**Claude.** `approval_request.prompt` is the Bash tool's `description`, not
the command. The command is in the sibling `command_execution.input`. Join
on `nativeItemRef.nativeId`, or use the approval node's `parentNodeId`.

**Codex.** `prompt` is the full command.

**Title.** It starts from `titleSeed` and is later replaced by a generated
title. `latestVisibleMessage` stayed `null`.

## 8. Provider session id (live)

**Where it is.** `projection.providerThreads[].nativeThreadRef.nativeId`.
It equals the Claude Code session id (the session file name) and the Codex
rollout id.

- It is stable across runs.
- It is `null` (`status:"not_loaded"`) until the first turn.
- When a thread has several provider threads, pick the one whose `id`
  equals `thread.activeProviderThreadId`.

**Not in the shell.** The shell entry has only the opaque
`activeProviderThreadId`, so getting the native id needs a thread
subscription or `getThreadProjection`.

**`providerSessionId` is a different thing.** It is a T3-internal id.

**Entrypoint.** The Claude session recorded `entrypoint:"sdk-ts"`.

## Contradictions with spec §6.5

1. **`waiting` does not mean needs-you.** Derive needs-you from
   `pendingRuntimeRequest != null`. Treat `waiting` with no request as
   working.
2. **Missing framing details.** The spec omits the required per-Chunk `Ack`
   and the `Fail`/`Die`/`Interrupt` failure shapes.
3. **Resume never errors.** Project-only snapshots must not replace state.
4. **No payload check on a reused `commandId`.** acd's own
   `duplicate_mismatch` check (§7.4) is required.
5. **A restart cancels a pending request** (`not_resumable`).
6. **`message.dispatch` fields.** It requires `messageId`, `createdBy`,
   `creationSource`, `attachments` and `dispatchMode`.
7. **Ownership rule 1** can be implemented, but only through thread detail.
8. **Claude approval detail** must be joined from `command_execution`.
9. **No `options[]` from either provider**, so the spec's fallback options
   apply.

## Not verified

- Multi-select questions.
- The `acceptForSession` and `acceptAlways` decisions.
- The statuses `preparing`, `queued`, `failed`, `interrupted` and
  `rolled_back`.
- Replay past the fallback thresholds.
- Concurrent responds.

## Race gate (Task 8, 2026-10-08)

**Serialization point (read-only source inspection).** Extracted the installed
Nightly bundle with `npx --yes @electron/asar extract` into
`/tmp/acp4b/asar`; extracted JavaScript was only read. In
`apps/server/dist/binCli-CZU3Kebe.mjs`, `dispatchWithReceipt` wraps the
command effect in the per-thread `ThreadCommandExecutor` lock:

> `const dispatchWithReceipt = (command) => threadDispatch.withLock(commandThreadId(command), dispatchWithReceiptEffect(command));`

The request handler checks `runtimeRequest.status !== "pending"` before
emitting a resolved runtime-request event; `dispatchWithReceiptEffect`
commits the events and command receipt while still inside the lock. This is
the serialization boundary for two commands on one thread. The wire failure
schema carries a `cause` array, so multiple causes are representable. No
concurrent failed dispatch was captured here to establish whether this
specific path emits multiple causes.

**Implementation.** `crates/acd-adapters/tests/t3_live.rs` holds two ignored
tests:

- `concurrent_raw_responds_have_one_winner` uses two independent T3
  connections and a barrier.
- `acd_and_raw_client_race_in_both_orders` uses acd/1 plus a raw T3 client,
  in the order given by `T3_LIVE_ORDER`.

**Run.** A throwaway server ran on port 47992 with its data in `/tmp/acp4c`.
acd ran on loopback port 47810 with herdr disabled. Every approval came from
a fresh CODEX thread in `approval-required` mode. A small driver created
each thread, sent a `touch` command and waited for `pendingRuntimeRequest`.
One approval took about 4 to 8 s.

**Results** (2026-10-08, 15:37–15:40):

| Check | Runs | Result |
|---|---|---|
| Raw race (`accept` vs `decline`, barrier) | 10 | 10/10 had exactly one `Success`. The loser was classified `request_gone` (terminal), and the projection's decision was the winner's. |
| Raw first, then acd | 1 | The projection recorded `decline`. acd returned `request_gone`, and clients saw `request.resolved {by: "terminal"}` with no `option_id`. |
| acd first, then raw | 1 | The projection recorded `accept`. The raw respond was classified `request_gone`, and clients saw `by: "inbox", option_id: "accept"`. |
| Simultaneous acd and raw | 10 | 10/10 attributions matched the projection. In all 10 the raw client won (`decline`, acd `terminal`). acd's path is slower by a round trip, so the simultaneous runs never produced an acd win; the acd-first run covers that outcome. |

No run produced two `Success` exits, and no attribution contradicted the
projection.

**acceptForSession.** Two fresh approvals were answered with
`acceptForSession`. T3 returned `Success`, recorded `decision:
"acceptForSession"`, and the command ran (the file was created). It stays in
the fallback set.

**Gate verdict: PASS.** 22 of 22 runs passed.

**Tooling bugs fixed on the way.** These were problems in the tests and the
driver, not in the adapter:

- The live tests now take the full WebSocket URL.
- They read `projection` at the top level of a thread snapshot item.
- They use a fresh acd command id per run (the idempotency cache correctly
  rejected a reused id as `duplicate_mismatch`).
- They check the late raw respond by its classification. The error's Display
  is a fixed string.

**History.** A first live run executed no races. A second run, on Codex Sol,
was refused partway through by the model provider's safety filter.

## Live smoke test (Task 8, 2026-10-08)

All T3 commands used `T3CODE_HOME=/tmp/acp4b/t3home`; the server was started
with the required `t3 serve --base-dir /tmp/acp4b/t3home --port 47991
--host 127.0.0.1 --no-browser /tmp/acp4b/proj`. Before the smoke checks,
`curl http://127.0.0.1:47991/` returned HTTP 200. acd used a temporary
`ACD_CONFIG_DIR` under `/tmp/acp4b` and its token scoped to
`orchestration:read` and `orchestration:operate`.

- `acd status`: **PASS** — `t3=Ok`; the Claude smoke thread appeared as an
  agent in `/tmp/acp4b/proj`.
- Claude Bash approval: **PASS** — acd/1 showed a pending `permission`
  request with `answer_path: "t3"` and detail
  `touch /tmp/acp4b/proj/x-claude-smoke.txt\nCreate smoke test file`.
  Answering `accept` returned `delivered`, resolved `by: "inbox"`, and the
  file existed afterward.
- Claude AskUserQuestion: **PASS** — acd/1 showed the question and options
  `o1`/`o2`; answering `o1` returned `delivered` and resolved `by: "inbox"`
  with `option_id: "o1"`.
- `agent.send`: **PARTIAL** — command returned `delivered`; Claude replied

- Restart while pending: **PARTIAL** — a CODEX Bash permission was observed
  pending before stopping and restarting the throwaway T3 server. After

  pending request. The transient `degraded`/`unknown` states and
  `request.resolved {by: "lost"}` were not captured by a continuously

A direct `t3 project remove /tmp/acp4b/proj` attempt returned
`invalid_command`; the shell subscription showed snapshots but no
