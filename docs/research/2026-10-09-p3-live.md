## 14. Registry entry delay (LIVE CHECK 14, release gate)

Method: `/tmp/acp3/live/reg.py` forks `claude --model haiku --permission-mode default --settings <managed
settings.json>` on a pty (all `CLAUDE_*` variables removed), taking `time.time()` immediately before the fork,
then polls `~/.claude/sessions/<pid>.json` every 3 ms. Delay = first time the file exists minus the fork time. The
entry's own `startedAt` minus the fork time agreed within 3 to 5 ms; `ps -o lstart=` (UTC) matched to the second.
The registry is the real `~/.claude/sessions` because a scratch config dir cannot log in. Each session was closed
with `/exit` (all entries removed; no `kill -9`). Raw rows: `/tmp/acp3/live/reg-results.jsonl`.

| Scenario | Sessions | Min | Median | Max | Load average (1 min) |
|---|---|---|---|---|---|
| Idle machine, one session at a time | 15 | 0.609 s | 0.664 s | 0.971 s | 4 to 5 (the user's own work; not zero) |
| During `acd token rotate hook --force` in a loop (115 rotations, mean 0.13 s, max 0.37 s, all exit 0) with 4 sessions started at once, 3 rounds | 12 | 0.754 s | 1.201 s | 1.253 s | about 7 |
| Under load: a fresh `cargo build --release -p acd` in a loop plus 4 busy-loop shells, 8 sessions started at once, 3 rounds | 24 | 2.010 s | 2.368 s | **3.062 s** | 19 at start, 66 after the run |

The entry exists before it has a `status`: at first sight no sample had one; `status: idle` followed 0.2 to 0.4
s later when idle, up to 5.29 s later under load (max `idle_after`). The scan in `claude_sessions.rs` does not need a
status: it needs `pid`, `sessionId` and a verifiable `procStart`; an entry that is half-written or lacks
`procStart` makes the scan incomplete, which only delays retirement.

**Verdict.** `REGISTRY_GRACE_MS = 5000` holds in all three scenarios: worst delay 3.06 s, margin 1.94 s (the grace
is 1.63 times the worst delay), and 5.1 times the idle worst case. The margin is thinner than it looks if the
machine is worse than this run (load average 66 on 8 cores was already heavy) or if Claude does more work before writing the entry (hooks in user settings ran in all sessions; a
slower network or a cold disk is not covered). A larger grace costs only a later retirement. This supports
5000 ms with margin for the release gate; consider 10 s if you want a margin of 3x at no cost.

## Consequences

Bugs (evidence above):

1. **`acd service install` over a loaded job fails about half the time** with `Bootstrap failed: 5: Input/output
   error` and leaves the service unloaded (2 of 4 reinstalls of a loaded job). launchd's `bootout` finishes
   asynchronously; `bootstrap` right after it races. Fix: wait until `launchctl print` stops finding the label
   (bounded, about 5 s) after `bootout`, or retry `bootstrap` on error 5, and fail with a clear message if it
   still fails. A first install and a reinstall of an unloaded job are fine.
2. **Codex dialogs are not detected in panes of about 50 columns or less** (the last option's `(esc)` wraps onto its
   own row and `scan_options` stops on it). The request falls back to `blocked_unparsed`, read-only, which is safe
   but needlessly strict. Fix in `screen.rs`: allow trailing continuation rows before the first option found
   (indented deeper than the option rows) or treat a lone `(key)` row as a description. Add a fixture from
   `/tmp/acp3/live/narrow-codex-detection.txt`.

Spec changes and decisions to make:

3. **§6.1 Token storage / gate 2a.** Qualify "Claude snapshots the hook configuration": on 2.1.296 a running
   session picked up the rewritten project-local `settings.local.json` (via symlink) on its next hook, while a
   `--settings <file>` session never re-reads it, not even after `/clear`. Inferred from acd's pending count; capture the
   header on the wire before relying on it. The installer only writes the user settings file, which was not tested
   in place (the scratch config dir cannot log in).
4. **§6.1 Retention (T4).** Because every live registry session is counted, any Claude session that never sends an
